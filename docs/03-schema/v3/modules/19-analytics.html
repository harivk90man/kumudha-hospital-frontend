v3 Schema Module 19 · Analytics

Analytics & Reporting

Owner-dashboard configuration and pre-aggregated materialized views. Three regular tables (owner-editable config) + six materialized views (MV-backed dashboard widgets).

Design principle: MVs are projections of OLTP tables — they add no new data, only pre-aggregated reads. Dashboard widgets read MVs; transactional writes hit source tables (Modules 07–18). Source tables are authoritative; any MV can be dropped and recreated from scratch at any time.
v3 delta from TSD-14: tenant_id dropped from all tables and MV definitions (single-tenant deployment). gen_random_uuid() → uuidv7(). is_active boolean on alert_rules → deleted_at / deleted_by soft-delete. varchar → text. decimal(12,2) → numeric(14,2). MV source queries updated: segment now from invoice_items.item_type (no payment_items bridge — dropped); pharmacy expiry references drug_catalogue / drug_stock_ledger (not v2 medicines / stock_movements).

  • No target-setting requirement in Phase 1. Owner has not asked for "achieved vs target" comparison widgets yet.
  • MVs still work without it. mv_revenue_daily and mv_revenue_by_doctor provide actual revenue numbers independently.
  • Re-add in Phase 2 when the owner dashboard UI is built and the owner wants to configure monthly revenue thresholds by department or doctor. TSD-14 §6 open note flags the approval model question to resolve at that point.
announcements — deferred.
  • No in-app announcement UI in Phase 1.
  • Re-add when the owner / admin needs to broadcast messages to staff (maintenance windows, holiday notices, safety alerts).
alert_rules — deferred.
  • No alert evaluator job in Phase 1. The job requires a scheduler (Spring Quartz or pg_cron), notification infrastructure, and a UI for owners to configure thresholds — none of these are in Phase 1 scope.
  • Re-add together with the owner dashboard and the notifications module (Module 04, also deferred).
Materialized Views — deferred.
  • Phase 1: dashboard queries run directly against invoices, invoice_items, and payments. At Kumudha's volume this is fast enough.
  • When to add: when dashboard queries become slow under load — add a Spring Quartz job (or pg_cron) that calls REFRESH MATERIALIZED VIEW CONCURRENTLY on a schedule and switch dashboard queries to the MVs. Zero changes to any transactional table.
  • 3 MV specs locked below — column shapes are agreed so the batch job can be built without revisiting the schema.
MV specs (build when ready)
mv_revenue_daily hourly refresh when built

One row per (revenue_date, segment). Covers: revenue total, revenue by category (consultation / lab / radiology / pharmacy / ambulance / other), for any date range.

ColumnTypeMeaning
revenue_datedateinvoices.invoice_date — financial reporting date
segmenttextinvoice_items.item_type — consultation | lab_test | lab_panel | drug | radiology | ambulance | other
gross_revenuenumeric(14,2)Sum of line totals before whole-bill discount
discount_totalnumeric(14,2)Per-line discounts + proportional whole-bill discount
net_revenuenumeric(14,2)gross_revenue − discount_total
invoice_countintDistinct invoices in this date × segment bucket

Source: invoices JOIN invoice_items WHERE payment_status IN ('finalized','paid','partially_paid'). Unique index: (revenue_date, segment).

mv_collections_daily hourly refresh when built

One row per (collection_date, payment_mode). Covers: revenue by mode of payment — cash, UPI, card, cheque, etc. for any date range.

ColumnTypeMeaning
collection_datedateDate of payments.paid_at
payment_modetextpayments.payment_mode — cash | upi | card | cheque | bank_transfer | other
total_collectednumeric(14,2)Sum of payments.amount WHERE payment_direction = 'in'
total_refundednumeric(14,2)Sum of payments.amount WHERE payment_direction = 'out'
net_collectednumeric(14,2)total_collected − total_refunded
transaction_countintNumber of payment transactions in this bucket

Source: payments WHERE deleted_at IS NULL. Unique index: (collection_date, payment_mode).

mv_revenue_by_doctor hourly refresh when built

One row per (period_year, period_month, doctor_id). Monthly grain — daily per-doctor is too sparse. Covers: revenue per doctor for any month or year range.

ColumnTypeMeaning
period_yearintCalendar year
period_monthintCalendar month (1–12)
doctor_iduuidReferences users(id)
consultation_countintConsultations completed in this period
consultation_revenuenumeric(14,2)Net consultation invoice lines for this doctor
total_revenuenumeric(14,2)Total net revenue attributed to this doctor

Source: invoices JOIN invoice_items JOIN consultations. Unique index: (period_year, period_month, doctor_id).
