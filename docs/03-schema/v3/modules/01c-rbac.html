1. roles mutable L1 audit L3 audit soft-delete

Coarse functional buckets a user can hold. A user may have more than one role (e.g. a doctor who also runs the cash counter). Flat — no hierarchy / inheritance. Sub-grading like "junior consultant" lives in department_heads.role_type (Slice 1B), not here.

2. user_roles mutable L1 audit L3 audit soft-delete M:M bridge

Many-to-many bridge: a user can hold multiple roles; a role can be held by many users. Composite primary key on (user_id, role_id) — CONVENTIONS.md §2 allows composite PKs only on true M:M bridges. No surrogate id.

is_primary flag: exactly one active row per user must have is_primary = true, enforced by a partial unique index. This primary role is returned in the login response and drives UI portal routing (which portal the user lands on after login). Secondary roles grant additional permissions without changing the portal. When a new role assignment is made primary, the caller must first clear is_primary on the current primary row.

Columns (table-specific; uniform block also present)
ColumnTypeNullConstraintDefaultComment
user_iduuidNOPK part 1, FK → users(id) CASCADE—The user. CASCADE: hard-deleting a user removes their role assignments.
role_iduuidNOPK part 2, FK → roles(id) RESTRICT—The role. RESTRICT: a role still held by someone cannot be hard-deleted; soft-delete or reassign first.
is_primarybooleanNO—falseTrue on exactly one active row per user — enforced by uq_user_roles_primary partial unique index. Identifies the role used for login response and portal routing.

+ the 7 uniform audit + soft-delete columns (created_by doubles as "assigned by"; created_at doubles as "assigned at"; deleted_at = role revoked).

Constraints & Indexes
  • pk_user_roles — PRIMARY KEY (user_id, role_id)  — composite, no surrogate
  • uq_user_roles_primary — UNIQUE INDEX (user_id) WHERE is_primary = true AND deleted_at IS NULL  — enforces at most one primary role per active user; partial so revoked rows don't block re-assignment
  • ix_user_roles_role — INDEX (role_id) WHERE deleted_at IS NULL  — reverse-direction lookup: "who currently holds role X?"
Triggers
  • tr_user_roles_bu_touch — BEFORE UPDATE → fn_touch_updated()
  • tr_user_roles_au_audit — AFTER INSERT/UPDATE/DELETE → fn_audit_row()

3. role_permissions mutable L1 audit L3 audit soft-delete M:M bridge

What each role can do — one row per (role × table) with CRUD boolean flags. Composite primary key on (role_id, table_name). The vocabulary is fixed at 4 actions (C/R/U/D) forever — no Java enum maintenance, no DB↔enum drift. State-transition gates like "sign prescription" / "approve lab result" / "narcotic dispense" are not permissions here; they're enforced by DB triggers + Layer 2 maker-checker CHECKs.

Columns (table-specific; uniform block also present)
ColumnTypeNullConstraintDefaultComment
role_iduuidNOPK part 1, FK → roles(id) CASCADE—The role. CASCADE: hard-deleting a role removes its permission grants.
table_nametextNOPK part 2—Target table name (e.g. patients, prescriptions). Loose text — app-layer validates against the live schema; no FK to information_schema. Max length enforced by Postgres itself (63 chars).
can_createbooleanNO—falseINSERT rights on the table.
can_readbooleanNO—falseSELECT rights on the table.
can_updatebooleanNO—falseUPDATE rights on the table (including soft-delete by setting deleted_at).
can_deletebooleanNO—falseHard DELETE rights — rare in clinical/financial data; almost always false.

+ the 7 uniform audit + soft-delete columns (created_by doubles as "granted by"; deleted_at = grant revoked).

Constraints & Indexes
  • pk_role_permissions — PRIMARY KEY (role_id, table_name)  — composite, no surrogate
  • chk_role_permissions_at_least_one — CHECK can_create OR can_read OR can_update OR can_delete  — a row must grant at least one action; otherwise it's noise
  • ix_role_permissions_table — INDEX (table_name) WHERE deleted_at IS NULL  — reverse-direction lookup: "which roles grant any action on table X?"
Triggers
  • tr_role_permissions_bu_touch — BEFORE UPDATE → fn_touch_updated()
  • tr_role_permissions_au_audit — AFTER INSERT/UPDATE/DELETE → fn_audit_row()
