1. patients mutable L1 audit L3 audit soft-delete

One row per patient. UHID is generated at registration from the format defined in hospital_profile (uhid_prefix, uhid_separator, uhid_sequence_padding, uhid_include_year). Allergies and chronic conditions are normalised to child tables (patient_allergies, patient_chronic_conditions) — not stored as arrays on this row.

2. patient_govt_ids mutable L1 audit L3 audit soft-delete

Government-issued identity documents for a patient. One row per document type. CASCADE child of patients — hard-deleting a patient removes their ID records. The is_primary flag marks the document shown on prescriptions and billing forms.

Aadhaar note: UIDAI regulations discourage storing the full 12-digit Aadhaar number. Store only the last 4 digits for Aadhaar rows (e.g. XXXX-XXXX-7890) — the app enforces this mask; the schema stores whatever text the app provides.

id_numbertextNOCHECK length 1–50—Document number as printed. For Aadhaar, store masked form only (last 4 digits visible).

3. patient_merges mutable L1 audit L3 audit L2 maker-checker soft-delete

Records a duplicate-patient merge operation. The primary patient survives; the secondary is soft-deleted after merge. All clinical records (visits, prescriptions, lab orders) belonging to the secondary are re-pointed to the primary by the merge service. The before_state snapshot enables an unmerge if the merge was made in error — restores the secondary patient and reverses the record re-pointing.

One of the 7 Layer 2 maker-checker tables — the user who identifies the duplicate (created_by) cannot be the same user who approves it (approved_by).

primary_patient_iduuidNOFK → patients(id) RESTRICT—The surviving patient. RESTRICT: cannot delete the primary while a merge record exists.
secondary_patient_iduuidNOFK → patients(id) RESTRICT—The duplicate being merged in. Soft-deleted by the merge service on approval.
merge_reasontextYES——Free-form note explaining why the two records are believed to be duplicates
before_statejsonbNO——Full snapshot of the secondary patient row at the time of merge. Used by the unmerge operation to restore the secondary patient.

4. patient_allergies mutable L1 audit L3 audit soft-delete

One row per active allergy for a patient, linked to the allergies_lookup catalogue (Module 06). Replaces the v2 patients.allergies text[] column — each row carries clinical detail (severity, observed reaction, onset, source) that a flat array cannot express. Soft-deleting a row records that the allergy was removed or overridden; the history remains for audit.

5. patient_chronic_conditions mutable L1 audit L3 audit soft-delete

One row per chronic condition for a patient, linked to the chronic_conditions_lookup catalogue (Module 06). Replaces the v2 patients.chronic_conditions text[] column — each row captures clinical detail (diagnosis date, severity, controlled status, resolution) that a flat array cannot express. A resolved condition is marked is_resolved = true rather than soft-deleted, preserving the medical history on the patient chart.

6. uhid_sequences append / update

One row per calendar year. The service atomically increments last_seq using INSERT … ON CONFLICT DO UPDATE RETURNING — safe under concurrent registrations, no explicit locking required. The formatted UHID is assembled in UhidService using the format columns in hospital_profile (uhid_prefix, uhid_separator, uhid_sequence_padding, uhid_include_year).

Columns
ColumnTypeNullConstraintDefaultComment
yearintNOPK—Calendar year (e.g. 2026)
last_seqbigintNO—0Last issued sequence number for this year. 0 = no patients yet.
Atomic increment SQL
INSERT INTO uhid_sequences (year, last_seq)
VALUES (:year, 1)
ON CONFLICT (year)
DO UPDATE SET last_seq = uhid_sequences.last_seq + 1
RETURNING last_seq;
