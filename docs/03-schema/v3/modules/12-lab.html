1. lab_tests mutable L1 audit L3 audit soft-delete

Reference catalogue of every diagnostic test the lab can perform. Flyway-seeded with common tests; admin can add hospital-specific ones. Reference ranges (ref_min/max_male/female) and critical thresholds (critical_low/high) drive the auto-flag trigger on lab_results — a result outside critical thresholds raises an immediate alert to the senior reviewer.

Paediatric ranges note: the current design uses adult M/F ranges only. Paediatric and pregnancy-specific ranges (e.g. TSH in pregnancy, HCG) are clinically significant. A child table lab_test_reference_ranges can be added later for age-stratified ranges without touching this table — flagged as a future enhancement.

2. lab_test_groups mutable L1 audit L3 audit soft-delete

Panel and package definitions — bundles of individual tests sold together at a package price (e.g. CBC = Hb + WBC + Platelets + PCV, Diabetes Panel = FBS + HbA1c + Urine Routine). The doctor orders the panel; the system fans out to individual lab_order_items automatically.

TSD's test_ids UUID[] is replaced by the child table lab_test_panel_items — one row per constituent test with a sequence number for report ordering. This avoids array columns on Hibernate-written tables and enables per-item sequencing.

Panel pricing is centralized in services via service_id — same pattern as individual tests.

4. lab_orders mutable L1 audit L3 audit soft-delete

One order header per ordering event. A single order can contain multiple tests (each as a lab_order_items row). Status tracks the order through the full lab workflow — from creation through payment, sample collection, processing, and result release.

payment_required_before_service is dropped — all services require payment first per system_config key. ordered_at is dropped — created_at from the uniform block is the order timestamp. invoice_id is set once the billing counter raises the invoice (forward FK to Module 17).

Forward FK note: invoice_id references invoices(id) defined in Module 17. FK constraint added in the Module 17 migration.

Status lifecycle
  • ordered → patient sent to billing
  • ordered → paid — invoice settled; lab notified to proceed
  • paid → sample_collection — patient at lab counter
  • sample_collection → sample_collected — phlebotomist collected sample
  • sample_collected → in_progress — lab processing started
  • in_progress → partially_reported — some tests done, others pending
  • partially_reported → reported — all tests done, pending senior review
  • reported → released — senior verified and released; doctor's inbox updated
  • Any → cancelled

collected_at is dropped — created_at from the uniform block is the collection timestamp. collected_by is kept as an explicit column because clinical accountability for sample collection is separate from who entered the record into the system.

7. lab_results mutable L1 audit L3 audit L2 maker-checker soft-delete

One row per test result. The lab tech enters the result; the auto-flag trigger compares value_numeric against the gender-aware reference ranges on lab_tests and sets flag automatically. Critical values trigger an immediate alert to the senior reviewer. Layer 2 maker-checker governs the verification workflow — the doctor's inbox only shows results with release_status = 'verified' or 'override_released'.

performed_by is kept explicit (clinically accountable actor). created_at from the uniform block serves as both the performed and reported timestamp — no separate performed_at / reported_at columns.

Result corrections use the self-FK amended_from_result_id — a corrected result chains to the original; both rows are preserved.

Verification workflow (Layer 2)
  • Tech enters result → row created; release_status = 'pending_verification', approval_status = 'pending_approval'
  • Critical flag → immediate alert fires to senior reviewer regardless of release status
  • Senior verifies (normal) → approval_status = 'approved', release_status = 'verified', verified_by / verified_at set. Result visible to doctor.
  • Senior requests correction → approval_status = 'rejected', rejection_reason set. Tech re-enters → new row with amended_from_result_id pointing to original.
  • Override release (critical value released as-is) → release_status = 'override_released', is_override_release = true, override_release_reason mandatory. Flagged prominently in compliance reports.
  • CHECK: created_by <> verified_by — tech who entered ≠ senior who released.
