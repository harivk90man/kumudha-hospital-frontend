v3 Schema Module 18 · Payments & Cash

Payments & Cash

Money movement — collection, allocation across invoices, per-source revenue breakdown, cash counter registry, cashier shift lifecycle, and non-sale cash movements.

Design overview:
  • Two-phase payment model: payment_attempts tracks every attempt (initiated → success/failed/expired) with the gateway idempotency key. payments (the financial ledger) only gets a row on confirmed success. Failed attempts leave no trace in payments or invoices.
  • payment_attempts is generic across all service types — one row covers appointments, lab orders, radiology orders, and pharmacy sales via separate-column FKs (exactly one non-null, enforced by CHECK). This replaces the per-table payment_attempt_key approach.
  • payments records every confirmed money movement (in = collection, out = refund/payout). payment_allocations splits one payment across multiple invoices or pharmacy sales.
  • Revenue-by-source (consultation, lab, pharmacy, radiology) is derived from invoice_items.item_type — no separate bridge tables. This keeps Module 18 focused on money movement only.
  • Pharmacy return refund traceability: payments.pharmacy_return_id → pharmacy_returns — when a cashier refunds cash/UPI for a pharmacy return, the payments row (payment_direction = 'out') carries pharmacy_return_id directly.
  • payees table deferred: For Phase 1, payments carries patient_id + walk_in_name + walk_in_mobile directly. The payees table will be added when vendor refunds, employee advances, or insurance settlements become active requirements.

The payments table covers all current use cases by carrying patient_id (for registered patients) and walk_in_name + walk_in_mobile (for walk-in OTC customers) directly. A separate payees normalisation table should be introduced when any of the following become active requirements: vendor refunds (e.g. return to supplier), employee salary advances, insurance settlement payouts, or other non-patient money movements. At that point, payments.payee_id → payees(id) replaces the inline walk-in fields, and a migration populates historical rows.

2. payment_attempts mutable L1 audit

One row per payment attempt, across every service type that requires upfront payment — OPD appointments, lab orders, radiology orders, and pharmacy sales. Exactly one source FK column must be non-null, enforced by a CHECK constraint. The gateway_idempotency_key is generated by the app before calling the payment gateway and stored here so that any retry (after a timeout) sends the exact same key, preventing double-charge at the bank level.

Only status = 'success' rows ever link to a payments row. Failed and expired attempts carry no financial weight — they exist solely for the idempotency and retry mechanism, and as an operational audit trail ("why did this patient's card fail?").

Lifecycle: initiated (INSERT on payment start) → success (UPDATE when gateway confirms; payment_id set in the same transaction that creates the payments row) | failed (UPDATE when gateway definitively declines) | expired (UPDATE by a cleanup job when an initiated row is never resolved). A new attempt after failure = new INSERT with a new gateway_idempotency_key.

No soft-delete: payment attempt rows are never removed. No deleted_at / deleted_by columns. L1 audit block is reduced: created_by, created_at, updated_by, updated_at, version only.

Cash payments: no real gateway is involved. The app still INSERTs a payment_attempts row with status = 'initiated' and immediately UPDATEs to success in the same backend transaction after the cashier confirms. gateway_ref and gateway_response are NULL. This keeps the path uniform and gives idempotency on backend retries.

Supersedes payments.idempotency_key and invoices.idempotency_key: backend retry protection is now handled by checking payment_attempts.payment_id IS NOT NULL (already processed) instead of the per-table idempotency key columns. Those columns are candidates for removal in a follow-up migration.

3. payments mutable L1 audit soft-delete

One row per money movement — either a collection from a patient or walk-in customer (payment_direction = 'in') or a refund or payout (payment_direction = 'out'). Amount is always positive; direction is captured in payment_direction. Every payment belongs to a cash session. For registered patients patient_id is set; for walk-in OTC customers walk_in_name is set instead — exactly one must be non-NULL (enforced by CHECK constraints).

v3 delta from TSD: tenant_id dropped. payee_id dropped (payees table deferred) — replaced by patient_id + walk_in_name + walk_in_mobile directly on this table. paid_at dropped — use created_at from L1 audit block. pharmacy_return_id added for pharmacy return refund traceability.

idempotency_key status: payments.idempotency_key is a candidate for removal in a follow-up migration. Backend retry protection is now handled by payment_attempts.payment_id IS NOT NULL — if that FK is already set, the payment was already processed and the existing data is returned without re-inserting. The column is kept for now to avoid a breaking migration during active development.

4. payment_allocations append-only L1 audit

Splits one payment across multiple invoices, pharmacy sales, or IP admissions. For example, a single ₹560 UPI payment for an OPD visit might allocate ₹300 to the consultation invoice and ₹260 to the lab invoice — two rows here, one row in payments. The allocation_type column controls which FK column must be set, enforced by CHECK constraints. Corrections are made by inserting a reverse allocation row — UPDATE and DELETE are blocked by trigger.

Append-only: a BEFORE UPDATE OR DELETE trigger raises an exception on any attempt to modify or remove an allocation row. Corrections must be applied via a reversal allocation row (same amount, opposite payment with payment_direction = 'out').

Note: credit_note_id and a 'credit_note_application' allocation type are pending the Module 17 credit_notes decision — not included here yet.

Trigger function — fn_update_invoice_paid_amount()

Fires on every payment_allocations INSERT where invoice_id IS NOT NULL. Keeps invoices.amount_paid and invoices.payment_status consistent without any application-layer UPDATE. Same principle as fn_recompute_invoice_totals() on invoice_items.

AFTER INSERT ON payment_allocations
IF NEW.invoice_id IS NULL → skip (pharmacy_sale or on_account allocation)

v_paid := SELECT COALESCE(SUM(amount), 0)
          FROM payment_allocations
          WHERE invoice_id = NEW.invoice_id
            AND deleted_at IS NULL

UPDATE invoices
SET amount_paid    = v_paid,
    payment_status = CASE
        WHEN v_paid = 0            THEN 'draft'
        WHEN v_paid < total_amount THEN 'partially_paid'
        WHEN v_paid >= total_amount THEN 'paid'
    END
WHERE id = NEW.invoice_id

Why SUM instead of amount_paid + NEW.amount? A SUM recompute from all allocations is idempotency-safe — if a retry causes a duplicate allocation that the DB catches with a constraint, there is no phantom increment. It also correctly handles soft-deleted allocations (deleted_at IS NOT NULL excluded from the SUM) when a reversal is processed.

12. cash_sessions mutable L1 audit soft-delete

Cashier shift open/close cycle — the unit of daily cash reconciliation. One session per cashier per shift per counter. A cashier opens a session with a float, collects payments, then closes it with a physical count. The system computes expected_cash from all cash-mode payments in the session; the cashier enters counted_cash; variance is generated. Any non-zero variance requires a variance_reason. Once locked by the nightly job, the session is immutable.

One open session per counter: the partial unique index uq_cash_sessions_counter_active (counter_id WHERE status = 'open') ensures at most one cashier holds an open session at any counter at a time. A second cashier cannot open the same counter until the first session is closed. Combined with uq_cash_sessions_cashier_active (opened_by WHERE status = 'open'), the pair enforces: one counter, one cashier, one session at a time in both directions.

Session lifecycle is decoupled from login: a cashier may log out for a break and back in — their session stays open at the counter because sessions are tied to the cashier UUID (opened_by), not to the JWT. There is no handover endpoint — shift changes use independent open + close: A closes their session, B opens a new session later and enters the cash they physically count in the drawer.

Custody gap visibility: when B opens a counter, the system looks up the last closed session at that counter and stores it in previous_session_id. If B's opening_float differs from the previous session's counted_cash, B must provide an opening_variance_reason. This makes any unattended cash gap formally documented and attributable — A is clean (their close record), B is clean (they counted and explained), management has the discrepancy on record.

State machine: open → closed → reopened → closed → locked. The locked state is set by the daily-close batch job and is irreversible. Only supervisor roles may reopen a closed session.

v3 delta: tenant_id dropped. status values and session_label values lowercased. variance is a generated column. previous_session_id and opening_variance_reason added for custody chain visibility. uq_cash_sessions_counter_active index added. Handover API dropped — open + close only.

cash_counter_handovers append-only L1 audit API endpoint dropped

API endpoint dropped — table retained in DB only. The POST /api/cash-sessions/handover endpoint has been removed. Shift changes now use independent open + close:
  1. Cashier A closes their session (POST /api/cash-sessions/close) — enters counted cash; any variance is recorded against A.
  2. Some time later, Cashier B opens a new session (POST /api/cash-sessions/open) — enters the cash they physically count in the drawer; any gap from A's counted amount is documented via opening_variance_reason on the new session and linked via previous_session_id.
The cash_counter_handovers table and its Java entity/repository remain in the codebase for historical rows and potential future reporting. No new rows are written by the application.

Originally designed to atomically link an outgoing cashier's closing session to an incoming cashier's opening session in one transaction. Replaced by the simpler open + close model with cash_sessions.previous_session_id for custody chain traceability.
