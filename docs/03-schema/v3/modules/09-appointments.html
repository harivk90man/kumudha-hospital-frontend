v3 Schema Module 09 · Appointments

Appointments

The booking layer in front of an OPD encounter — slot grid, booked appointments, and queue tokens.

Module 09 contents — one table at a time
  1. appointments — booked appointment; channel, visit type, cancellation tracking  signed off
  2. appointment_slots — doctor's daily slot grid (available / booked / blocked / cancelled)  signed off
  3. tokens — issued queue tokens (D-04, L-12, P-08); never reused  signed off

1. appointments mutable L1 audit L3 audit soft-delete

One row per booked appointment. Pinned to a slot (slot_id) which is the source of truth for date and time — scheduled_at denormalises the slot start for fast sorting. Records the booking channel so owner reports can split traffic by source (walk-in vs phone vs online). Cancelled and no-show rows are kept for audit and analytics.

Forward FK note: slot_id references appointment_slots(id) defined later in this module. The FK constraint is added in the appointment_slots migration.

2. appointment_slots mutable L1 audit L3 audit soft-delete

One row per time slot per doctor per day. Generated by a scheduled job from doctor_profiles.available_days × slot_duration_mins for the next N days. A slot is available (open for booking), booked (one appointment attached), blocked (admin reserved — leave / surgery / training), or cancelled (slot withdrawn). FK target for appointments.slot_id.

Constraints & Indexes
  • pk_appointment_slots — PRIMARY KEY (id)
  • chk_appointment_slots_status — CHECK status IN ('available','booked','blocked','cancelled')
  • chk_appointment_slots_duration — CHECK duration_mins > 0
  • chk_appointment_slots_blocked — CHECK status = 'blocked' OR blocked_reason IS NULL  — blocked_reason only meaningful when status is blocked

3. tokens mutable L1 audit L3 audit soft-delete

The visible queue identifier shown on corridor display boards and called out to patients. One token per service request — D-04 for consultation with a doctor, L-12 for lab, P-08 for pharmacy, X-03 for radiology, B-07 for billing. Tokens are never reused — a cancelled token's sequence number stays cancelled for that day so the same number is never called twice.

Each token links back to exactly one parent entity via a dedicated FK column. The service_type and the populated FK column must agree — enforced by per-type CHECK constraints.

Forward FK notes: lab_order_id, radiology_order_id, pharmacy_sale_id, and invoice_id reference tables defined in Modules 12, 13, 15, and 17 respectively. FK constraints are added in those migrations.

Constraints & Indexes
  • pk_tokens — PRIMARY KEY (id)

  • chk_tokens_status — CHECK status IN ('active','called','completed','cancelled','no_show')
  • chk_tokens_sequence — CHECK token_sequence > 0
  • chk_tokens_exactly_one_parent — CHECK num_nonnulls(op_visit_id, lab_order_id, radiology_order_id, pharmacy_sale_id, invoice_id) = 1
  • chk_tokens_consultation_fk — CHECK (service_type = 'consultation') = (op_visit_id IS NOT NULL)
  • chk_tokens_lab_fk — CHECK (service_type = 'lab') = (lab_order_id IS NOT NULL)
  • chk_tokens_radiology_fk — CHECK (service_type = 'radiology') = (radiology_order_id IS NOT NULL)
  • chk_tokens_pharmacy_fk — CHECK (service_type = 'pharmacy') = (pharmacy_sale_id IS NOT NULL)
  • chk_tokens_billing_fk — CHECK (service_type = 'billing') = (invoice_id IS NOT NULL)
  • uq_tokens_with_provider — UNIQUE INDEX (service_type, provider_id, issue_date, token_sequence) WHERE provider_id IS NOT NULL  — consultation tokens: no duplicate sequence per doctor per day
  • uq_tokens_no_provider — UNIQUE INDEX (service_type, issue_date, token_sequence) WHERE provider_id IS NULL  — counter tokens: no duplicate sequence per service per day
  • ix_tokens_op_visit — INDEX (op_visit_id) WHERE op_visit_id IS NOT NULL
  • ix_tokens_live_queue — INDEX (service_type, provider_id, status, issue_date) WHERE status IN ('active','called')  — live queue board per service / doctor
